0→1フェーズのモバイルアプリ向けに `DESIGN.md` を生成するスキルです。
最小限の入力からデザインシステム全体を推論し、性格の異なる3案を提示します。

## 参照ファイル一覧

| ファイル | 内容 | 読むタイミング |
|---|---|---|
| `references/preview-html.md` | プレビューHTML生成仕様（レイアウト・CSS変数切り替え） | Step 2 でHTMLを生成する直前 |
| `references/design-md-format.md` | DESIGN.md 出力テンプレート（プリミティブ生成ルール含む） | Step 4 でDESIGN.mdを書き出す直前 |
| `references/tokens-json-format.md` | tokens.json 構造テンプレート（Token Studio互換） | Step 4 でtokens.jsonを書き出す直前 |

## Step 1: コンテキスト収集

### ファイルが渡された場合（`$ARGUMENTS` にパスあり）

`Read` ツールでファイルを読み込み、以下を抽出する：

- アプリ名・サービス名
- ターゲットユーザー・ペルソナ（年齢層・ITリテラシー・利用シーンなど）
- アプリのジャンル・カテゴリ
- トーン・雰囲気に関するキーワード
- ブランドカラーの言及（あれば）
- ベンチマーク（目標・手本とする）アプリ（あれば）
- 競合・参考サービス

抽出後、プラットフォームのみユーザーに確認する：

> 「資料を読み込みました。開発プラットフォームを教えてください：Flutter / React Native / SwiftUI / Jetpack Compose」

### ファイルがない場合（`$ARGUMENTS` が空）

以下を **1問ずつ** 聞く（全3問）：

**Q1:** アプリの名前を教えてください。

**Q2:** 開発プラットフォームを選んでください。

1. Flutter 2. React Native 3. SwiftUI 4. Jetpack Compose

**Q3:** アプリの世界観・雰囲気をキーワードや参考アプリで教えてください。
（例：「信頼感・落ち着き・ビジネス向け」「ポップ・楽しい・ゲーム系」「ミニマル・シンプル」「高級感・洗練」）

## Step 2: 3つのデザイン案を推論・提案

収集したコンテキスト（世界観・ターゲット・ジャンル）を分析し、**性格の明確に異なる3案**を提示する。

### 提案時のデザイン思考

3案を生成する際は、以下の観点を自然に取り入れる：

- **ペルソナ起点**: ターゲットユーザーが日常的に使い慣れているアプリの操作感・視覚言語を意識する。提案の理由には「このペルソナにとってなぜ良いか」を含める
- **参考アプリの活用**: ベンチマークアプリや同ジャンルの大手アプリのデザイン傾向を参考にしつつ、独自性を持たせる
- **認知負荷への配慮**: 色数・情報量・視覚的な複雑さを適切に抑え、ユーザーが迷わず操作できるデザインを心がける
- **トレンドの反映**: 現在のモバイルUIトレンド（例：ニューモーフィズム、グラスモーフィズム、大きなタイポグラフィ、ゆとりのある余白など）を適度に取り入れる

### 案の差別化ルール

|                | 案A               | 案B                  | 案C                |
| -------------- | ----------------- | -------------------- | ------------------ |
| 基本方向       | 信頼・落ち着き系  | 活気・エモーション系 | 上品・プレミアム系 |
| 彩度           | 中〜低            | 高                   | 低〜中             |
| 角丸           | シャープ（4-8px） | 丸み重視（20px+）    | 標準（12-16px）    |
| フォントの太さ | 標準〜細め        | 太め・個性的         | 細め・エレガント   |

世界観・ジャンルに強い制約がある場合（例：子ども向けなら全案で丸みを持たせる）は柔軟に調整する。

### グラデーションの扱い

グラデーションは各案で「使う／使わない」を判断する。使う場合は以下を守る：

- **用途を限定する**: CTAボタンやアクセント装飾など、さりげない箇所に絞る。画面全体をグラデーションにしない
- **自然な色の遷移**: ベースカラーの同系色（色相を少しずらす、明度・彩度を変える）で構成する。離れた色相同士の組み合わせは避ける
- **グラデーション色はセマンティックカラーとは別に定義する**: 既存のPrimary/Secondaryをそのまま端点にせず、グラデーション専用の2色を設計する

## Step 3: WCAGコントラスト比の自動検証（必須ガードレール）

**DESIGN.md生成前に必ずこのステップを実行する。**

### 計算方法

各Hex値（#RRGGBB）を以下の手順でコントラスト比を計算する：

1. R, G, B を 0〜1 に正規化（÷255）
2. 各チャンネルを線形化：
   - `c <= 0.04045` → `c_linear = c / 12.92`
   - `c > 0.04045` → `c_linear = ((c + 0.055) / 1.055) ^ 2.4`
3. 相対輝度：`L = 0.2126*R + 0.7152*G + 0.0722*B`
4. コントラスト比：`(L_明 + 0.05) / (L_暗 + 0.05)`

### 検証対象

| 組み合わせ                       | WCAG AA 基準                 |
| -------------------------------- | ---------------------------- |
| テキスト（High）on Background    | 4.5:1 以上（通常テキスト）   |
| テキスト（High）on Surface       | 4.5:1 以上                   |
| White（or On Primary）on Primary | 4.5:1 以上（ボタン文字）     |
| Primary on Background            | 3:1 以上（UIコンポーネント） |

### 問題がある場合の警告フォーマット

> 「コントラスト比の警告」
>
> - `#XXXXXX`（テキスト）on `#XXXXXX`（背景）= **X.X:1**（WCAG AA 4.5:1 未満）
>
> 代替案：`#XXXXXX` に変更すると **X.X:1** となりWCAG AAを満たします。採用しますか？

ユーザーが確認・承認してから Step 4 へ進む。
問題がなければ「コントラスト比はすべてWCAG AAを満たしています」と報告してから進む。

## Step 4: DESIGN.md と tokens.json の生成・保存

1. `references/design-md-format.md` を読み込み、テンプレートに従って `DESIGN.md` を生成・保存する

## 保存完了後のメッセージ

> `DESIGN.md` と `tokens.json` をプロジェクトルートに保存しました。
>
> **次のステップ:**
>
> 1. `CLAUDE.md` に以下を追記すると、AIが自動でルールを参照します：
>    ```
>    UIの実装・修正前に必ず DESIGN.md を読み込み、定義されたトークンとルールに従うこと。
>    ```
> 2. `tokens.json` は **Token Studio for Figma** でそのままインポートできます。Figma プラグインの「Import」からファイルを選択してください。
> 3. デザインを変更したい場合は `/smart-design-md` を再実行するか、`DESIGN.md` と `tokens.json` を直接編集してください。
